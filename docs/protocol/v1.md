# OpenRTC Protocol v1 (Frozen for Beta)

This document defines the OpenRTC WebSocket protocol contract for v1.

## 1. Envelope (All Messages)

All messages use JSON objects with this envelope:

- `t` (string): message type.
- `id` (string): caller-generated correlation identifier.
- `room` (string, optional by type): target room name.
- `event` (string, optional by type): event name.
- `payload` (JSON, optional by type): type-specific body.
- `meta` (object, optional): metadata (trace fields, pagination cursor, etc.).

### Validation and normalization rules

- Non-JSON messages are rejected with `BAD_REQUEST`.
- Unknown top-level fields are rejected.
- `t` and `id` are required for all messages.
- `id` must be 1-128 safe ASCII characters.
- `room` is required for room-scoped messages, must be tenant-prefixed, and must be 1-256 safe ASCII characters.
- `event` is required only for `EMIT` (client) and `EVENT` (server).
- `event` must be 1-128 safe ASCII characters.
- `payload` is opaque JSON except where type-specific fields are required.
- Envelope size over 20 KB is rejected with `PAYLOAD_TOO_LARGE`.
- Payload size over 16 KB is rejected with `PAYLOAD_TOO_LARGE`.
- `id` is echoed in responses/errors whenever available.

## 2. Client -> Server Message Types

### `JOIN`

Required fields:
- `t = "JOIN"`
- `id`
- `room`

Optional fields:
- `meta.limit` (integer): capped snapshot page size.
- `meta.cursor` (string): pagination cursor.

### `LEAVE`

Required fields:
- `t = "LEAVE"`
- `id`
- `room`

### `EMIT`

Required fields:
- `t = "EMIT"`
- `id`
- `room`
- `event`
- `payload`

### `PRESENCE_SET`

Required fields:
- `t = "PRESENCE_SET"`
- `id`
- `room`
- `payload` (object state)

### `STORAGE_GET`

Required fields:
- `t = "STORAGE_GET"`
- `id`
- `room`

Returns the current room storage document as `STORAGE_SNAPSHOT`.

### `STORAGE_SET`

Required fields:
- `t = "STORAGE_SET"`
- `id`
- `room`
- `payload` (JSON object or typed storage root)

Optional fields:
- `meta.op_id` (string): client-generated mutation identifier echoed in the
  ack/update payload.

Creates or replaces the room storage document, validates typed storage shape,
acks the sender with `STORAGE_ACK`, and sends `STORAGE_UPDATE` to other joined
room connections.

### `STORAGE_PATCH`

Required fields:
- `t = "STORAGE_PATCH"`
- `id`
- `room`
- `payload` (JSON Patch operation array)

Optional fields:
- `meta.op_id` (string): client-generated mutation identifier echoed in the
  ack/update payload.

Applies a JSON Patch operation array atomically to the room storage document,
validates the final typed storage shape, acks the sender with `STORAGE_ACK`, and
sends `STORAGE_UPDATE` to other joined room connections.

Runtime storage messages require a matching `storage:<pattern>` scope or a room
access grant that permits storage through `room:write`.

## 3. Server -> Client Message Types

### `HELLO`

- Sent after successful auth.
- `payload` includes `conn_id` and server metadata.

### `ERROR`

- `payload.code` is a stable machine code.
- `payload.message` is human-readable.
- `payload.id` mirrors the triggering request id when provided.

### `JOINED`

- Confirms room membership.
- Includes snapshot page fields in `payload`:
  - `members`
  - `presence`
  - `next_cursor`

### `LEFT`

- Confirms room leave.

### `EVENT`

- Room event fan-out payload.

### `PRESENCE`

- Presence state update for a room.
- `payload.conn_id` identifies the connection whose presence changed.
- Online/update payloads include `payload.state`.
- Offline payloads include `payload.offline = true` and are sent on `LEAVE` or disconnect.
- The TypeScript Yjs SDK may reserve `__openrtc_yjs_awareness` inside presence
  state for provider-style awareness data. Awareness is ephemeral JSON presence,
  not part of the persisted Yjs document or durable storage APIs.

### `STORAGE_SNAPSHOT`

- Sent in response to `STORAGE_GET`.
- `payload.document` is the current storage document.

### `STORAGE_ACK`

- Sent to the mutating connection after `STORAGE_SET` or `STORAGE_PATCH`.
- `payload.kind` is `set` or `patch`.
- `payload.op_id` echoes `meta.op_id` when provided.
- `payload.document` is the authoritative storage document after the mutation.

### `STORAGE_UPDATE`

- Sent to joined room connections other than the mutating connection after a
  storage mutation.
- `payload.kind` is `set` or `patch`.
- `payload.op_id` echoes `meta.op_id` when provided.
- `payload.origin_conn_id` identifies the mutating connection when available.
- `payload.operations` is present for patch updates.
- `payload.document` is the authoritative storage document after the mutation.

## 4. Yjs Binary Sync

Yjs document sync uses a separate WebSocket endpoint:

- Path: `/yjs/{url-escaped-room}`
- Auth: same bearer/query JWT as `/ws`
- Read permission: `join` claim or room access grant must allow the room.
- Write permission: `publish` claim or room access grant must allow update
  frames and state-vector diff response frames for the room.
- Room names use the same validation rules as JSON room messages.
- Binary frames over `OPENRTC_LIMIT_YJS_MAX_BYTES` are rejected by the connection read limit.
- Yjs write frames are rate-limited with `OPENRTC_LIMIT_EMITS_PER_SECOND`.

After a successful connection, the server replays the persisted document:

1. Latest snapshot frame, if one exists.
2. Incremental update frames after the snapshot checkpoint.

Frames are binary. The first byte is the frame kind and the remaining bytes are
the frame payload:

- `0x01`: incremental Yjs update. Client-sent update frames are durable writes.
- `0x02`: full Yjs snapshot update sent by the server during replay when a trusted
  compactor snapshot exists.
- `0x03`: state-vector request. The payload is `Y.encodeStateVector(doc)`.
  Client-sent request frames are transient and relayed to other active Yjs
  clients in the room; they are not stored.
- `0x04`: state-vector diff response. The payload is
  `Y.encodeStateAsUpdate(doc, remoteStateVector)`. Client-sent diff frames are
  transient, require room write permission, and are relayed to other active Yjs
  clients in the room; they are not stored.

Clients may send `0x01`, `0x03`, and `0x04` frames. A full document state
generated by `Y.encodeStateAsUpdate(doc)` is still a Yjs update and should be
sent as `0x01` when it is intended to become durable room state. The runtime
stores only `0x01` update frames in a sequenced document log for reconnect replay
and rejects client-sent snapshot frames so ordinary clients cannot replace the
stored baseline. Transient state-vector frames are a live large-document
convergence optimization and are not a durability boundary. A trusted compactor
may merge known updates into a snapshot checkpoint and remove only updates at or
below that checkpoint. The in-repo `@openrtc/yjs-compactor` package is the
reference trusted compactor for Redis-backed deployments. Conflict resolution and
duplicate update handling are owned by Yjs on clients; OpenRTC relays, persists,
checkpoints, and fans out Yjs update bytes.

Client SDKs may also keep a local offline cache. The `@openrtc/yjs`
`offlineStore` option and `createIndexedDBYjsStore()` helper replay cached Yjs
updates before opening the websocket and append local/remote Yjs updates after
that. This cache is client-local only; it does not replace the runtime's
sequenced update log or trusted snapshot compaction.

Yjs awareness:
- `@openrtc/yjs` exposes `provider.awareness`, an awareness-compatible state map
  keyed by Yjs client ID.
- When a JSON protocol client is supplied to the provider, awareness updates are
  bridged through normal OpenRTC presence using `__openrtc_yjs_awareness`.
- Awareness liveness follows OpenRTC room membership and presence offline
  events. It is intentionally not stored in Yjs snapshots, Yjs update logs, or
  room storage documents.

## 5. Admin HTTP APIs

Admin APIs require the admin JWT issuer/audience and scoped room claims.

Room metadata lifecycle:
- `POST /v1/rooms` creates a durable room record. Body:
  `{"id":"tenant-a:room-1","metadata":{...},"defaultAccesses":["room:read","room:presence:write"],"usersAccesses":{"user-1":["room:write"]},"groupsAccesses":{"editors":["room:write"]}}`.
- `GET /v1/rooms/{url-escaped-room}` returns a room record.
- `PATCH /v1/rooms/{url-escaped-room}` updates room metadata and access
  grants. Body fields are optional and include `metadata`, `defaultAccesses`,
  `usersAccesses`, and `groupsAccesses`.
- `DELETE /v1/rooms/{url-escaped-room}` deletes the room metadata record.
- `GET /v1/rooms?prefix=tenant-a:&limit=50&cursor=0` lists room records by safe prefix.

Room metadata endpoints require a matching `rooms:<pattern>` scope, for example
`rooms:tenant-a:*`.

Room access grants:
- Access-token style claims (`join`, `publish`, `presence`, or scoped claims)
  are checked first.
- In cluster mode, if token scopes do not allow a client room action, the
  runtime checks the room record using the token subject and `groupIds`/`groups`
  claims.
- `room:write` allows join, publish/Yjs writes, and presence.
- `room:read` allows join/Yjs read.
- `room:presence:write` allows presence writes.
- Empty access arrays are private/deny entries. User grants override group and
  default grants; matching group grants override default grants.

Room storage lifecycle:
- `GET /v1/rooms/{url-escaped-room}/storage` returns the durable JSON storage document.
- `PUT /v1/rooms/{url-escaped-room}/storage` creates or replaces the storage document. The body must be a JSON object or a typed storage root.
- `DELETE /v1/rooms/{url-escaped-room}/storage` deletes the storage document.
- `PATCH /v1/rooms/{url-escaped-room}/storage/json-patch` applies a JSON Patch operation array atomically. Supported operations: `add`, `remove`, `replace`, `test`, `copy`, and `move`.

Storage endpoints require a matching `storage:<pattern>` scope, for example
`storage:tenant-a:*`. Patch paths use JSON Pointer escaping rules from RFC
6901. If any patch operation fails, the stored document is not changed and the
API returns `PATCH_FAILED`.

Typed storage:
- Plain JSON object roots remain supported for lightweight metadata and app-owned
  state.
- Liveblocks-style typed storage nodes use
  `{"liveblocksType":"LiveObject"|"LiveList"|"LiveMap","data":...}`.
- A typed root must be `LiveObject` with object `data`.
- `LiveObject` and `LiveMap` nodes require object `data`; `LiveList` requires
  array `data`.
- JSON Patch may mutate typed storage, but the final document must preserve all
  typed node shapes or the patch is rejected atomically.
- Objects containing `liveblocksType` are reserved for typed storage envelopes.

Room threads and comments:
- `GET /v1/rooms/{url-escaped-room}/threads` lists durable room threads with
  embedded comments.
- `POST /v1/rooms/{url-escaped-room}/threads` creates a thread. Body:
  `{"id":"thread-1","metadata":{...},"comment":{"id":"comment-1","userId":"user-1","body":{...},"metadata":{...}}}`.
  `id` fields are optional; the server generates safe IDs when omitted.
- `POST /v1/rooms/{url-escaped-room}/threads/{url-escaped-thread}/comments`
  appends a durable comment to a thread. Body:
  `{"id":"comment-2","userId":"user-2","body":{...},"metadata":{...}}`.
- Thread and comment metadata, plus comment bodies, must be JSON objects and
  are bounded by the configured payload limit.

Thread/comment endpoints require a matching `comments:<pattern>` scope, for
example `comments:tenant-a:*`. They are durable Redis-backed records and are
not delivered through the non-durable room event Pub/Sub path.

Inbox notifications and subscription settings:
- `POST /v1/inbox-notifications/trigger` creates a durable inbox notification.
  Body:
  `{"id":"in_1","userId":"user-1","kind":"$custom","subjectId":"subject-1","threadId":"thread-1","roomId":"tenant-a:room-1","activityData":{"count":1}}`.
  `id`, `subjectId`, `threadId`, `roomId`, and `activityData` are optional; the
  server generates a safe `in_` ID when omitted.
- `GET /v1/users/{url-escaped-user}/inbox-notifications` lists a user's durable
  inbox notifications. Query parameters: `limit` from 1-50, `cursor` or
  `startingAfter`, `query=unread:true`, and `unread=true`.
- `GET /v1/users/{url-escaped-user}/inbox-notifications/{url-escaped-id}`
  returns one notification.
- `DELETE /v1/users/{url-escaped-user}/inbox-notifications/{url-escaped-id}`
  deletes one notification.
- `DELETE /v1/users/{url-escaped-user}/inbox-notifications` deletes all
  notifications for the user.
- `POST /v1/inbox-notifications/{url-escaped-id}/read` marks one notification
  as read after loading the notification and checking user notification scope.
- `GET|POST|DELETE /v1/users/{url-escaped-user}/notification-settings` reads,
  replaces, and resets project-level notification settings as a bounded JSON
  object.
- `GET|POST|DELETE /v1/rooms/{url-escaped-room}/users/{url-escaped-user}/subscription-settings`
  reads, updates, and resets room subscription settings. `threads` may be
  `all`, `replies_and_mentions`, or `none`; `textMentions` may be `mine` or
  `none`.
- `GET /v1/users/{url-escaped-user}/room-subscription-settings` lists explicit
  room subscription overrides for a user.

Notification endpoints require a matching `notifications:<user-pattern>` scope,
for example `notifications:user-*`. Custom notification kinds must start with
`$` and contain only letters or underscores after `$`. `activityData` must be a
bounded JSON object with scalar values.

Active users:
- `GET /v1/rooms/{url-escaped-room}/active_users` returns currently active
  room members with connection ID, user ID, tenant/node metadata when available,
  connection time, and current presence state.

Active-user reads require a matching `presence:<pattern>` scope, for example
`presence:tenant-a:*`. The response is derived from Redis room membership and
heartbeat metadata, so clients should avoid high-frequency polling.

Existing admin live operations:
- `POST /v1/publish` broadcasts an ephemeral room event and requires `publish:<pattern>`.
- `POST /v1/presence` writes server-side ephemeral presence and requires `presence:<pattern>`.
- `GET /v1/stats` returns aggregate runtime/admin stats.

## 6. Compatibility

- v1 is non-durable and at-most-once.
- Ordering is guaranteed only per sender connection.
- Reconnect creates a fresh session; no resume window is supported.
- The JSON room/event protocol is non-durable. Yjs frames are persisted for room
  document replay.
